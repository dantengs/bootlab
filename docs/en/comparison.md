# bootlab compared with simpleboot and Hyperion

bootlab learned from two established frameworks: **simpleboot** (Ning Su; Mathematica) and the **Hyperion**
ecosystem (David Simmons-Duffin; Haskell: Hyperion, hyperion-bootstrap, bootstrap-bounds, scalars-3d,
stress-tensors-3d). This page says where bootlab follows them, where it differs, and what it does not have.
Statements about the other two come from reading their source code during bootlab's design; statements
about bootlab come from its specification and measurements. Nothing here is a benchmark between the three.

## In one table

| | simpleboot | Hyperion ecosystem | bootlab v1 |
|---|---|---|---|
| Language of the driver | Mathematica | Haskell (master and workers over Slurm, distributed-process) | Python, standard library only, one Slurm job per run |
| Search algorithms | feasibility, bisection, Delaunay, OPE scan, Navigator, Skydive, EFM | Navigator with BFGS (hyperion-bootstrap), Skydive (stress-tensors-3d), and others | **Skydive only** |
| Crossing equations | AutoEqu / VBlock in Mathematica | Haskell code per model (`ToSDP` instances) | JSON data (`bt-model/2`, simpleboot's VBlock conventions) |
| Spectrum assumptions | part of the Mathematica set-up | part of the bound's Haskell key | TOML data; values may be exact expressions of the point's parameters |
| External operators | scalars (other cases not studied for this comparison) | scalars, stress tensors, currents (blocks_3d) | d = 3 scalars only |
| Runs on | laptop (Docker) or cluster (Apptainer) | cluster, built per machine (`hyperion-config`) | Slurm cluster, one prebuilt image, site generated by a probe |
| Resource choice | user configuration | program configuration | from measured data (bench files, first-step memory) |

## Where bootlab follows them

- **Skydive semantics.** The loop (centre and `k` neighbours, one `dynamical_sdp` call per step, BFGS state
  passed from step to step, boundary finding) follows the reference Hyperion-based program's Skydive loop,
  which in turn follows simpleboot's driver. Option names map one to one.
- **Crossing-equation conventions.** The model format uses simpleboot's VBlock form (each channel gives a
  j × j matrix of F/H terms per equation), so simpleboot equations translate term by term. The two
  convention differences with the upstream blocks (λ ordering and its (−1)^ℓ; the prefactors of mixed
  correlators) are handled once in the generator and were checked against simpleboot on the Ising
  system and on a larger mixed system.
- **Σ navigator normalization** is simpleboot's `SigmaNavigatorNormalizer` (same sign: N < 0 allowed). A GFF
  normalization in the style of Hyperion's Ising navigator is also available; on three Ising points it agreed
  with the reference program's built-in GFF navigator to 29–32 digits.
- **Block truncation presets**: simpleboot's (by Λ) and Hyperion's (by nmax).
- **The numerical code of PMP generation is Hyperion's.** The generator in the image is scalars-3d with a
  small entry point; its PMP parts for the centre point are byte-for-byte those of the reference program.

## Where bootlab differs

**Inputs are data, checked once.** All three physics files are data; `inputs.load` checks them once and
lists every error (unknown keys, wrong spins, a gap set twice, TOML floats that already lost digits), before
anything is submitted. Spectrum values are exact expressions of point parameters (a parameter that is not a
model coordinate becomes an extra search coordinate), evaluated with exact rational arithmetic. In
Hyperion a new model is Haskell code; in simpleboot it is Mathematica code.

**Numbers stay exact.** Points, neighbours (`x + ε eᵢ`) and spectrum values are exact decimals; records keep
every digit as strings. The regression requires agreement with the reference program to ≥ 130 digits at every
step (the remaining difference: the reference forms the neighbours in 512-bit binary floating point).

**Endings are explicit.** Every run ends with one written outcome: `converged` (allowed, excluded or
boundary, after checking that the primal and dual objectives have the same sign), `stopped` (left the box,
N undecided at optimal, negative N), `unfinished` (step, iteration or time limit; solver stall) or `failed`
(a program failed). simpleboot's Skydive driver stops on any solver ending other than "update" without telling
them apart, and does not check a box. Nothing in bootlab is retried automatically.

**Defaults that differ from simpleboot's Skydive driver** (each can be set back in `run.toml`):

| | simpleboot driver | bootlab |
|---|---|---|
| finite-difference step ε | 1e-40 | 1e-20; below 1e-25 refused, because the generator keys block tables by about 31 digits of Δ12 (simpleboot passes Δ12 to scalar_blocks with 50 digits, so 1e-40 is safe there) |
| gap upper limit | `Automatic[1]`: the first call only | the first call's value, then it tracks N: `min(limit, max(c·|N_prev|, κ·|N_1|, 1000·floor))`; `"off"` gives the fixed or first-only behaviour |
| stopping threshold | the solver option, fixed | tightened with N: `max(1e-30, min(setting, 1e-3·|N_prev|))`; can be switched off |
| iteration count passed to the solver | 0 at every call | cumulative |
| box | not checked | `stopped: left box` when x + Δx leaves it |
| boundary direction gate | after a step with Dobj < 0 | after a step with N < 0 (`find_boundary_when_allowed`), or from the first step |

**Restarts survive any kill.** The solver's checkpoint is written straight into the run directory, and for
each record bootlab keeps that solve's generation with hard links (`checkpoint/kept/<k>`). A resume, by
hand, goes back to the last record's generation and warm-starts; this was tested with SIGKILL in the middle of
writing a checkpoint. In simpleboot a killed point is first drawn back and the same task submitted again.

**Resources come from measurements.** Solver processes, `pmp2sdp` instances at once and the number of nodes
for one solve are chosen from measured data; `pmp2sdp`'s memory is measured in the first step, and a watchdog
cancels a wave before memory runs out (where `pmp2sdp` would stall rather than fail). Only physical cores are
used.

**The generator's scheduling is bootlab's.** The numerical code is upstream's; the scheduling around it was
changed where measurements showed waiting, with parts byte-for-byte unchanged each time:

| Change | Measured (one step, 128 cores) |
|---|---|
| the Σ normalization split into single terms on all cores, summed in upstream's order (bootlab's first generator used the upstream scheduling unchanged) | Ising Λ = 19: 701.7 s → 66.1 s |
| each point's plan computed once, on a worker, in parallel; normalization pieces dispatched first | a 7-coordinate model at Λ = 23, 8 points: 1310.7 s → 670.6 s |

**Portable by probing.** `bootlab probe` measures node types, InfiniBand ports, scratch disks and the
network; `bootlab site gen` writes the site from it, with the basis of each choice. The host needs only Slurm
and Apptainer. A Hyperion program is configured and compiled per machine; simpleboot ships Docker and
Apptainer workspaces.

## What bootlab does not have (yet)

- Any algorithm other than Skydive: no Navigator, feasibility scans, bisection, Delaunay, OPE scans or EFM.
- simpleboot's extra Skydive driver features (GCP scanning and sticking, β override after climbing,
  starting from an earlier `SDPBReturn`).
- External operators with spin, and other dimensions.
- Interactive use: no notebook front end, no laptop mode; every run is a Slurm job.
- A converter from simpleboot files in this release; a published execution image.
- Tests on more than one cluster.

simpleboot and the Hyperion ecosystem are mature research tools used for many published results; bootlab v1
is a narrow, new code base. Use it where its Skydive and its records suit the work, and compare with the
established tools when in doubt.
